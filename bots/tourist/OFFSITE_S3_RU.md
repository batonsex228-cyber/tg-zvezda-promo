# «Турист» v0.12.0 — автоматические зашифрованные внешние копии

**Это необязательный режим для Linux VPS с Docker Compose.** Бот, обычный Mini App, Caddy и Windows `.bat` работают без него. **Подключение настоящего S3 и восстановление на другой машине ещё не проверены:** в этом релизе проведены локальные тесты с подменённым S3-клиентом. До ввода в эксплуатацию настройку нужно проверить на принадлежащем Вам хранилище.

## Для чего это нужно

Локальная SQLite и папка `/app/backups` могут погибнуть вместе с VPS. Дополнительный контейнер `offsite` получает **только доступ на чтение к базе SQLite**, делает SQLite Online Backup, создаёт **AES-256-GCM** архив, загружает **только шифрованный `.tbackup`** в S3 и скачивает его обратно для проверки размера и SHA-256. Обычные `.sqlite3` **не отправляются**. Промежуточные файлы удаляются после успешной и ошибочной попытки.

Защита данных зависит от сохранности парольной фразы. Пароль нельзя восстанавливать из архива. Создайте бумажную/офлайн-копию фразы **вне VPS** и обеспечьте безопасный доступ уполномоченному владельцу.

## Подготовка хранилища

1. Создайте **частный** bucket в AWS S3 или совместимом сервисе. Заблокируйте публичный доступ. Включите **versioning**, если сервис поддерживает, и настройте правила хранения/lifecycle (например, 30–90 дней — срок согласуйте с клиентом). Сам проект **не удаляет внешние файлы автоматически**.
2. Выдайте отдельному IAM-пользователю только необходимые операции на ограниченный префикс: `PutObject`, `GetObject`, `HeadObject` (для S3 IAM `HeadObject` покрывается `s3:GetObject`). Для S3-провайдеров могут потребоваться дополнительные разрешения или серверное шифрование SSE-S3/AES256; проверьте совместимость. Не выдавайте `DeleteObject`, доступ к другим bucket или администраторские роли.
3. Скопируйте `offsite.env.example` в `offsite.env` **только на VPS**. Внесите bucket, префикс, регион и учётные данные. Для AWS оставьте `OFFSITE_S3_ENDPOINT_URL` пустым; для совместимого сервиса допускается **только HTTPS** на стандартном порту 443. Храните файл с правами `chmod 600 offsite.env` и не помещайте в Git.
4. Создайте `secrets/offsite_passphrase.txt` с **одной длинной непредсказуемой фразой** (не менее 14 символов; рекомендована существенно большая длина). Не используйте токен Telegram, пароль VPS или пароль Google. Файл на VPS: `chmod 600 secrets/offsite_passphrase.txt`. В контейнер он подключается как read-only Docker Compose secret, а не через аргументы командной строки.
5. Храните **копию** парольной фразы вне сервера. Также сохраните инвентаризацию: кто имеет доступ к bucket, где находится офлайн-пароль и кто отвечает за восстановление.

В `offsite.env`:

```dotenv
OFFSITE_S3_BUCKET=private-club-backups
OFFSITE_S3_PREFIX=tourist/
OFFSITE_S3_REGION=eu-central-1
OFFSITE_S3_ENDPOINT_URL=
OFFSITE_INTERVAL_HOURS=24
AWS_ACCESS_KEY_ID=ВАШ_ОТДЕЛЬНЫЙ_КЛЮЧ
AWS_SECRET_ACCESS_KEY=ВАШ_ОТДЕЛЬНЫЙ_СЕКРЕТ
```

Не отправляйте этот файл мне или кому-то в переписку.

## Запуск

Обычный сервис уже должен работать через `docker compose up -d --build`. Не останавливая его, выполните **из каталога проекта**:

```bash
mkdir -p secrets
chmod 600 offsite.env secrets/offsite_passphrase.txt
docker compose -f compose.yaml -f compose.offsite.yaml --profile offsite up -d --build offsite
# Проверка логов без раскрытия ключей
docker compose -f compose.yaml -f compose.offsite.yaml logs --tail=30 offsite
```

**Важно:** профиль отдельный. Не включайте `offsite` несколько раз на параллельных VPS, пишущих в один bucket. При ошибке загрузки процесс делает следующую попытку, сохраняя предыдущую отметку об успешной выгрузке. Успех фиксируется только после обратного скачивания и сравнения шифрованных байтов.

Статус для владельца появляется в Mini App → **Админ → Обзор → Состояние системы**. Он сообщает только время последней подтверждённой выгрузки, **не** ключи и пути. Отсутствие отметки означает «не подтверждена», а не «бакет пуст». При отсутствии связи с хранилищем локальный бот продолжает работать.

## Отказ и восстановление после потери VPS

1. На **другом** компьютере под контролем владельца получите нужный `.tbackup` из частного bucket через официальный S3-клиент/панель. Убедитесь, что доступ к копии не публичный. Возьмите пароль из отдельного безопасного хранилища.
2. Установите зависимости из `requirements.txt`, расположите `.tbackup` в закрытой папке и запустите `python -m scripts.encrypted_backup import /путь/copy.tbackup /путь/НОВАЯ.sqlite3`. Введите пароль **интерактивно**. Старая база никогда не перезаписывается.
3. Проверьте напечатанные результаты проверки таблиц и привязки к **тому же BotFather-токену**. Верните файл на новый защищённый сервер, а `DATABASE_PATH` измените только после остановки прежних процессов. Проверьте владельца, профили, игры, заявки, Google Sheets, очередь сообщений.
4. Если новый VPS подключается к тому же токену, **старый экземпляр обязательно отключите**, иначе Telegram long polling будет конфликтовать. Если меняете владельца бота/токен — **не переносите админские права и очереди вслепую**; следуйте инструкции миграции.

**Ограничения:** проверка SHA-256 загруженного и скачанного файла подтверждает совпадение байтов при этой операции, но не гарантирует будущую доступность или сохранность bucket. Не реже раза в месяц проводите **на другой машине** полный тест скачивания и расшифровки. Доступность объектов, права хранилища, ротация ключей, политика персональных данных и реальные сертификаты HTTPS проверяются отдельно.

## Безопасность

- Не храните ключи AWS в `.env` основного приложения: их получает только дополнительный контейнер из `offsite.env`.
- Не включайте публичные ACL. Для совместимого S3 требуется поддержка `ServerSideEncryption: AES256`.
- Не удаляйте локальные и старые проверенные резервные копии до успешной проверки внешнего восстановления.
- Не пытайтесь открыть SQLite в Windows через сетевую папку как рабочую базу: восстанавливайте файл локально.
- На VPS храните временные незашифрованные snapshots только в защищённом Docker volume; они очищаются по завершении экспорта. `root`/администратор VPS в принципе может читать работающую БД, поэтому разграничение серверного доступа важно даже при шифрованном внешнем архиве.
